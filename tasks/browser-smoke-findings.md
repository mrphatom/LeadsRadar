# Browser smoke findings

On 2026-08-23, the local development server responded at `http://127.0.0.1:3000/` with the expected title `LeadsRadar | AI-Driven Outreach Lead Generator`, but the viewport was completely blank and no interactive elements were detected. Browser HTML was saved at `/home/ubuntu/browser_html/127_0_0_1_page_1787516904674.html` for inspection. This is a reproduction of a client startup/render failure and must be localized before release.
The browser console showed only the standard React DevTools info, but a controlled root inspection returned `readyState: complete` and `rootHtml: null`. The HTML contains the expected `/src/main.tsx` module, so the failure occurs before React mounts or in module evaluation. The server log shows Vite started successfully; the unrelated Vite HMR WebSocket reported port 24678 already in use.
Reloading the local app reproduced the blank viewport with the same title and no interactive elements. Browser console still reported only the standard React DevTools informational message, with no visible exception. The failure is therefore likely a module graph/runtime loading problem that the browser adapter is not surfacing directly.
A temporary `window.error` and `unhandledrejection` listener was armed before reload. The reload again produced a blank viewport and no interactive elements. The browser adapter still did not expose the captured error, so this smoke failure needs an alternate local reproduction path rather than being declared fixed.
Dynamic import of `/src/main.tsx` returned the exact error `@vitejs/plugin-react can't detect preamble. Something is wrong.` This confirms the root cause: the custom Express + Vite middleware server was not calling `vite.transformIndexHtml`, so the React Fast Refresh preamble was absent. `server.ts` was patched to transform `index.html` for HTML GET requests in development mode and to register the Express error handler after the final static/dev handlers. TypeScript validation passed after the patch.
The transformed HTML included the React refresh preamble, but dynamic import still returned `@vitejs/plugin-react can't detect preamble`. The remaining cause was the global Helmet CSP (`script-src 'self'`) blocking the required inline Vite preamble in development. `server.ts` now keeps full Helmet CSP in production and disables only the CSP middleware in development, while retaining the other Helmet protections. TypeScript validation passed.
After the development-only CSP patch, reload still showed a blank viewport and dynamic import still returned the React preamble error. The next check is the active server response headers/process state; the running `tsx` process may not have restarted its application module after the source edit.
After restarting the local server with the patched code, the authentication screen mounted successfully. Browser extraction showed the evidence-first heading, Sign In/Register controls, email/password fields, Google sign-in, and guest access. Clicking Register successfully rendered the conditional Full Name field, Apply Registration action, and console notice. The prior blank-screen defect is fixed locally. The browser screenshot viewport was 896×768; the compact card remained centered and usable.
With the fresh server restart, the browser rendered the authentication screen correctly again. The browser console still shows a non-fatal `[vite] failed to connect to websocket` warning, even when the smoke process is started with `DISABLE_HMR=true`; this is isolated to the development HMR client and does not affect production builds. The UI itself mounts and responds.
The final no-HMR smoke reload rendered the authentication screen successfully with the updated copy and controls. The browser adapter still reports a non-fatal Vite WebSocket warning, likely from its persistent browser session/cache or the Vite client injected by an earlier page; the current HTML should be checked to confirm the disabled-mode script is absent. No application UI failure was observed after the middleware/CSP fixes.
Custom Vite middleware mode preserved the successful authentication render. The browser console shows the React DevTools info and the same non-fatal Vite WebSocket warning; the application has no visible failure. The warning is likely from the persistent browser session or an injected Vite client outside the custom HTML handler and is not present in the production build path. The important pre-mount defect is resolved.

## Expanded release-pass smoke check — 2026-08-23

A clean local development server was restarted with HMR disabled on port 3000. The HTML response contained the current evidence-first title and `/src/main.tsx`, but the browser document reached `readyState: complete` with an empty `#root` and no visible interactive elements. The browser console did not report a captured runtime exception; DOM inspection confirmed `body.innerText` and `#root.innerHTML` were empty. A cache-busting reload reproduced the same state. Local server logs showed Firebase Admin initialized without a service account, Gemini initialized, and the server listening successfully; no secrets were inspected or changed. This is a current blocker for browser validation and must be localized before the UI changes are considered release-ready.

The current browser’s controlled dynamic import of `/src/main.tsx` failed with `TypeError: Failed to fetch dynamically imported module`, while a direct `fetch('/src/main.tsx')` returned HTTP 200 with `Content-Type: text/javascript` and Vite-transformed source. This narrows the issue to module-graph dependency loading or browser module evaluation rather than the HTML document itself.

Further browser diagnostics showed direct `fetch` requests for the transformed entry module, React dependencies, Firebase dependency, App, the shared subscription utility, SearchScanner, and AuthView all returned HTTP 200 JavaScript responses. However, dynamic imports of `/src/main.tsx`, `/src/App.tsx`, `/src/utils/subscription.ts`, `/src/components/SearchScanner.tsx`, and `/src/components/AuthView.tsx` all failed with the browser adapter’s opaque `TypeError: Failed to fetch dynamically imported module`. This suggests a browser module-policy or session-level loading issue affecting multiple modules, not a single JSX component; response headers and a fresh browser context are the next checks.

Opening the same clean no-HMR server through `http://localhost:3000` created a fresh browser origin and rendered the updated AuthView successfully. The DOM exposed `sign-in-tab` and `register-tab` with `role="tab"`, labeled email/password controls, and guest/Google actions. This indicates the prior blank root was isolated to the persistent `127.0.0.1` browser module-cache/session state; no current source-level blank-screen defect was observed on a fresh origin.

On the fresh localhost origin, clicking Register rendered the conditional Full Name field and registration notice without losing the surrounding controls. Clicking the password visibility control changed the password input from `type="password"` to `type="text"` and updated its accessible hint from “Show password” to “Hide password.”
